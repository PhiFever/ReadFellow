# MySQL 中间产物存储规格

日期：2026-09-08
状态：已实施并完成本机迁移。本文保留需求与决策；实际表结构及命令见 [MySQL 存储与查询](../mysql-storage.md)。

## 问题陈述

用户希望在开发和人工验证阶段，根据自己的阅读印象检查知识图谱中的人物关系。当前图谱、章节分析和切块元数据保存在 JSON / JSONL 中，临时联查、分组和统计需要自行解析、遍历，查资料和计算不方便。

用户已在 Windows 上长期运行 MySQL 服务，并使用 DataGrip 连接。因此本次直接采用 MySQL，不再比较数据库产品。讨论中的“SAG”已确认指知识图谱。

这里的“聚类查人物关系”指按人物、关系类型、章节组织查询，以及查看一跳、两跳关系，不包含自动识别人物社区或阵营的算法。

## 解决方案

通过 SQLAlchemy 将知识图谱、章节分析、原文切块和索引元数据直接存入 MySQL，应用日常读写也切换到数据库。实体、关系和证据采用可关联查询的结构，用户可以在 DataGrip 中写 SQL 检查结果，无需先解析整份 JSON。

保留各次抽取结果及其来源版本，用于人工比较。CLI 默认查询最新创建的抽取版本，包括尚未完成的版本，不自动回退旧版。已有 JSON / JSONL 一次性导入，避免重新调用模型。

zvec 继续承担向量检索和中文全文检索。源文档仍是事实依据，数据库保存的内容仍是派生物。

12. 作为项目使用者，我希望中断后续建同一版本，以便已完成的抽取不用重跑。

15. 作为检查历史结果的用户，我希望历史证据关联当时的原文切块，以便重新切块后不会串到新数据上。

18. 作为项目使用者，我希望失效检查和集合体检继续有效，以便知道数据是否可信、下一次运行能否续建。

## 实施决策

### 存储范围与架构

- 使用 SQLAlchemy 开发数据库模型和持久化逻辑，目标数据库为用户已有的 MySQL。
- MySQL 接管 manifest、原文 chunks、知识图谱和章节分析的日常持久化；不是只读查询副本，也不维持 JSON 双写或自动回退。
- zvec 的向量、中文 FTS 和现有 `ChunkStore` 接口继续保留。zvec 为检索返回原文而保存的字段继续存在，不要求把它变成只存向量的库。
- CLI 保持薄适配层，工作流仍由应用层编排。SQLAlchemy 会话和 ORM 对象封装在持久化层内，领域逻辑继续处理领域模型和 `Evidence`。
- 迁移需覆盖索引元数据读写、图谱及章节分析读写、构建与续建、图谱查询、hybrid 标注、源数据校验和集合体检。现有 `ChunkStore` 不涵盖这些全部职责，不能仅替换它的实现。
- 本次不改变抽取提示词、实体和关系归一规则、证据锚定规则、重试策略或采样参数。

### 关系数据与版本

- 实体、别名、类型、提及位置、关系和证据须能通过普通 SQL 关联查询，不把整份图谱塞入一个 JSON 列作为主要查询结构。模型参数等不参与核心关系查询的结构化配置可保留为 JSON 值。
- 章节分析保留摘要、人物、事件、顺序及 chunk 引用；每个已处理单元保留抽取计数、指纹与续建所需信息。
- 索引元数据和 chunk 组成有版本标识的源数据记录。保留源路径、source/text hash、切块设置、切块器版本、chunk 序号、章节、行号和字节位置。
- 每次新建抽取版本分配独立 `run_id`，记录集合、派生类型、源数据版本、模型、生成设置、格式版本、提示词版本、时间和处理进度。实体、关系等通过直接或间接外键归属于该版本。
- `run_id` 表示一次可续建的抽取版本，不替代已有格式版本和提示词版本；数据库自身的表结构演进也不与抽取版本混用。
- 图谱与章节分析可独立构建，各自按集合和派生类型确定最新版本；不要求为了更新其中一种产物重跑另一种。这是根据现有独立工作流作出的实施解释。
- 重建创建新版本并保留旧版本；中断续建沿用同一 `run_id`。CLI 默认选最新创建的版本，而不是最新完成或最近修改的版本，不因失败、未完成或失效自动回退。
- 历史版本关联当时的 chunk 记录，不能只按裸 chunk id 关联当前数据：重新切块可能使相同 id 对应不同文本范围。历史数据保留供 DataGrip 查询，CLI 不新增历史版本选择功能。
- 实体身份和关系关联不得跨运行版本混合；两跳查询也必须在同一版本内联接。表结构不得因外键约束丢掉现有关系端点桩或未声明实体。
- 保留既有 `unanchored_count = NULL` 的“未测量”语义；不得在导入或聚合时补成 0。拆表不等于补出了别名、类型的逐值来源。

### 写入、读取与原文约束

- 以现有图谱 chunk、分析章节为提交单元，将该单元的结果和完成记录放在同一事务中。读者可以看到部分已完成结果，但不能看到一个单元只写了一半。
- 模型生成不占用长时间数据库写事务。SQLAlchemy 负责短事务中的提交与回滚，续建依据已提交的处理记录。
- 最新版本尚无结果时如实报告空结果或进度；一旦已有结果即可查询。CLI 输出提供当前版本和处理进度。
- 保留源文档与派生物失效检查：读取时拒绝失效结果，构建时按现有规则决定续建或新建版本。历史保留不代表历史产物对当前源文件仍有效。
- `status` 继续报告失效原因，并以 zvec 实际存量对照数据库中的索引元数据。MySQL 事务不能覆盖 zvec 写入，不能因此宣称两种存储已实现原子发布。
- CLI 的证据仍回到所属 chunk 原文及精确出处；进度限制继续覆盖存储过滤和进程内过滤。受限图谱查询仍清空无逐值来源的别名、类型。
- hybrid 继续仅由向量和 FTS 两路召回与融合，图谱只标注；保留现有标注预算和失效时跳过标注并报告原因的行为。
- DataGrip 是用户主动使用的全量分析入口，自由 SQL 不受 CLI 阅读进度限制。

### 一次性导入

- 导入已有 manifest、chunks、graph 和 analysis，不调用模型，不重新生成 embedding。
- 将已有图谱和分析分别登记为历史运行记录，保留原模型、参数、版本、时间、进度、证据和计数，不能用当前配置覆盖旧记录的来源信息。
- 导入前核对产物之间的引用与指纹。不能确认来源的记录不得假装已通过校验；应报告具体原因，不静默关联到当前 chunk。只有现存数据支持时才能恢复历史，无法补出已丢失的切块版本。
- 导入不修改原始文件，保留其作为备份。切换后数据库是这些产物的日常存储入口。
- 导入事务与重复执行须避免半份数据和同一输入的重复记录；具体命令形态、识别方式及物理表名留给实施设计。

## 测试决策

以下方案已随实现落地：应用层共用可注入的 `ArtifactStore`，默认测试使用临时 SQLite，真实 MySQL 通过显式 `--mysql` 测试验收。

- 优先从应用层工作流验证外部行为，沿用 `ChunkStore`、`JsonGenerator` 和假 embedder 的注入方式，不断言 ORM 内部调用或 SQL 文本长相。
- 元数据及派生物建议共用一个可从应用层注入的持久化入口，由其封装 MySQL 事务。具体接口在实施时根据调用方确定，不为每张表分别增加测试接口。
- 沿用既有图谱和章节分析领域测试，覆盖解析、合并、证据、进度和失效语义；沿用应用层已有的图谱重建、原文回读、别名防剧透、hybrid 和 status 用例。
- 默认自动化测试继续不依赖 Ollama 或用户长期运行的 MySQL。另设显式执行的真实 MySQL 集成验收，使用独立测试库验证目标数据库行为，不以 SQLite 通过代替 MySQL 通过，也不操作用户已有业务表。
- 保留使用真实 zvec 的 CLI 测试，继续覆盖 optimize、重开、中文 FTS、进度过滤和 fetch 原文链路。
- 新增覆盖限于本需求的主路径和明确要求的错误行为，不扩展假设性的边界矩阵。

验收场景：

1. 导入已有产物后，实体、关系、章节分析、原文和来源字段与输入一致；旧计数的未知值仍是 `NULL`，不调用模型，重复导入不增加重复结果。
2. 提供可在 DataGrip 执行的查询示例：指定人物的一跳和两跳关系、按关系类型与章节统计、关联证据及原文；每条查询明确限定集合和版本，避免联接后重复计数。
3. 图谱与章节分析直接从数据库写入、重新打开读取及续建，日常流程无需读取旧 JSON 备份。
4. 重建后旧版仍可查询；续建不生成新版本、不重复写入已完成单元；CLI 使用最新版本，即使其未完成，也不回退旧版。
5. 重新切块后，旧运行仍关联旧 chunk，新旧证据不混用。
6. 单元提交失败时结果与处理记录一起回滚，再次运行可继续；此前成功提交的单元保持可读。这直接验证替代原有原子文件发布后的要求。
7. 源文档或派生指纹失效时保留原有拒绝查询、构建重建及 status 报告语义；导入发现引用不一致时明确报错，不伪造可用数据。
8. 现有原文引用、CLI 防剧透、hybrid 标注和真实 zvec 检索测试通过。

## 不在范围内

- 自动人物聚类、社区发现、阵营识别和重型 GraphRAG。
- 替换 zvec、改变向量或全文检索算法、把图谱重新加入 hybrid 召回评分。
- 保存模型原始回复、每次重试回复或被拒条目的完整内容。
- CLI 历史版本切换、多套历史向量索引、历史数据自动清理。
- JSON 与 MySQL 长期双写、查询副本同步、数据库不可用时自动回退文件。
- DataGrip 自由 SQL 的自动防剧透、图形化关系浏览界面。
- SQL 编辑抽取结果后反向同步到源文档或建立人工修订工作流。
- MySQL 与 zvec 的分布式事务或整体索引两阶段发布。
- 生产环境选型、独立二进制打包、部署与数据库服务安装。
