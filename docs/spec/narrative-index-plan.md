## 不重新讨论的事

- **核心需求是 E 类问题**：某段剧情或某个任务的**高光**，以及**人物塑造**。事实定位、关系查询、前情提要都是次要的。（Q1）
- **查询由 agent 规划**。ReadFellow 只提供精确、便宜、防剧透的基础命令。查询改写、HyDE、multi-query、工具内 LLM rerank 都不做。（Q2）
- **离线派生允许调用云端模型**，用 b.ai 上目前免费的 `qwen3.8-flash`，关掉思考模式，费用不构成约束。原定的 GLM 5.3 Flash 因账户没有余额，2026-09-14 实测后改定。查询时的 embedding 继续用本地 Ollama `qwen3-embedding:8b`。（Q3、Q9）
- **评估集先行**。任何会改变排序的改动都要在评估集上对比。例外：对错由三条不变量判定的修正，比如章节识别，不走评估集。（Q4）
- **离线只产原子笔记，由 agent 在查询时汇总**。不预先写人物小传或剧情段总结。短剧情段靠 `fetch-range` 让 agent 读原文。（Q7）
- **图谱冻结**：不再投入、不重建，现有产物继续给 `hybrid` 做标注。等新派生物在评估集上胜出，再决定是否退役。（Q8）2026-09-14 补记：第 2 步重建索引后，现有图谱已经失效，标注暂停，详见第 2 步。
- **原地升级 `analyze`**，不另建派生物。（Q12）
- **人物身份分两遍归并**。每条身份关系都带「在哪一章确立」，查询时只使用进度之内确立的关系。（Q13）
- **剧情段连续切分**，分「卷 → 剧情段」两层。只有整段读完的剧情段才会出现在输出里。（Q6、Q14、Q16）
- **防止模型把已知的后文写进笔记**，用确定性的人名检查兜底。（Q15）

## 为什么现有机制对不上 E 类问题

- **`hybrid` 返回最相似的前几个 chunk**（`search.top_k` 默认 5）。高光要的是覆盖一段剧情后按重要性挑选；人物塑造要的是全书分散的场景按时间排列。两者都不是相似度前几名。`hybrid` 仍然适合用来定位模糊描述的某一段。
- **图谱用封闭关系词表记录事实边**。被它当作叙事长尾丢掉的谓词（`怀疑`、`担心`、`回答`，全量占 20.7%）恰恰是人物塑造的素材。
- **`analyze` 是最接近的现有机制**：它逐章给出梗概、人物作用和事件，并且锚定了原文。但每章上限 8 个人物、10 个事件，没有重要度，也没有跨章结构。

## 已核实的事实

**zvec 按进度过滤是精确的。**
- `VectorSchema` 不传 `index_param` 时默认是 Flat 索引（`zvec/model/schema/field_schema.py:238-239`）。`store.py` 没有传。
- filter 在向量检索之前计算，检索过程中边查边过滤（`src/db/sqlengine/planner/vector_recall_node.cc:138,168-169`）。
- 在 0.6.0、2307 条 × 4096 维上实测：放行比例降到 0.9% 时 recall@20 仍为 1.000，越界 0 条。返回条数为 `min(topk, 可见文档数)`。
- 如果以后改用 HNSW，要重新验证。

**Qwen3-Embedding 的查询端 instruction。**
- 官方格式是 `Instruct: {task}\nQuery:{query}`。只加在查询端，文档端不加；中文任务的 instruction 也用英文写。
- 来源：https://github.com/QwenLM/Qwen3-Embedding README 第 93-94、103 行；`evaluation/task_prompts.json`。
- Ollama 的 `/api/embed` 不套用任何模板（v0.34.0 `server/routes.go:800-976`），前缀必须由调用方自己拼。
- 官方只笼统说能提升 1–5%，这本书上没有测过。

**Ollama 没有 rerank 端点（截至 v0.34.0）。**
- 相关需求 issue #3368 至今仍 open。
- `/api/generate` 从 v0.12.11 起支持 `logprobs`，理论上可以做 yes/no 打分，但没有验证。

**代码里的坑。**
- `read_text_units` 会丢掉空行，所以 `chunk.text` 里不含空行，在里面数换行得不到源文件行号。
- `chapter_char_budget` 按所选后端的 `num_ctx` 计算上下文预算（`num_ctx - num_predict - 600` 个 token）。调大 `num_predict` 会同时缩小能放进 prompt 的章节长度。

**云端生成端点**（2026-09-14 实测，探测脚本和原始输出没有入库）

- b.ai 的 `glm-5.3-flash` 现在用不了：账户余额为 0，请求返回 `insufficient_user_quota`。
- `.env` 里启用的是 AMD 开发者平台的 `DeepSeek-V4-Flash`，OpenAI 兼容接口，背后是 sglang router。下面五项都是在它上面测的：
  1. **不支持 JSON schema。** `response_format` 传 `json_schema` 直接返回 400（`does not support JSON schema output mode`），`/models` 也写着 `structured_outputs: false`。`json_object` 能用，但只保证输出是合法 JSON：让它照抄一个越界的 enum 值加一个多余字段，它原样照抄了。所以 `moments[].kind` 没法在解码阶段约束，只能解析后校验。
  2. **上下文。** `/models` 标称 1,048,576 token。实测发 146,820 字，计 81,954 个 prompt token，模型答对了首行和末行，没有从左侧截断。中文约 1.8 字/token（章节 prompt 实测 1.81），`CHARS_PER_TOKEN` 按 qwen 写的是 1.5。最长的一章 30,905 字，约 1.7 万 token。走这个端点不会有章节因超预算被跳过。云端后端的预算按 `openai.num_ctx`（65536）算，约 91,260 字，也放得下最长的一章。
  3. **并发和限流。** 响应头给了两个上限：每分钟 20 次（`x-ratelimit-limit-user-rpm`），每天 1 美元（`x-ratelimit-limit-user-daily-usd`，北京时间 10:41 左右重置）。同时发 24 个小请求，成功 8 个，其余 16 个立即返回 429 `token_concurrency_rate_limit_exceeded`，带 `retry-after: 1`。触发的是并发上限（约 8），不是每分钟上限。6 章并发分析时，单章 47–186 秒，解码 7–18 token/s，整批 186 秒；单独跑一章是 84 秒。
  4. **思考模式默认关闭。** 默认 `reasoning_tokens` 为 0。传 `reasoning_effort: "high"` 或 `chat_template_kwargs: {"thinking": true}` 会打开，产生 400–520 个思考 token，照样计费，`reasoning_content` 始终为空。传 `thinking` 字段返回 400。所以不需要关，只要不传这两个参数。
  5. **采样参数只认 `temperature`、`top_p`、`max_tokens`。** `/models` 的 `supported_parameters` 只列了这三个，外加 stream、response_format、tools。`top_k`、`min_p`、`presence_penalty`、`frequency_penalty`、`repetition_penalty`、`seed` 都返回 200，但不报错不等于生效：`top_k=1` 连跑 3 次，输出从第一个字起就不同，`seed` 也一样；`temperature=0` 连跑 3 次同样不可复现。`max_tokens` 传到 393,216 也照收。
- **冒烟调用通过。** 现有 `build_chapter_prompt` 加 `json_object`、temperature 0.7、top_p 0.8，跑「第二十一章 一枚芯片镇泥丸，由此我命不由人」（3 个 chunk，prompt 5,905 字）：耗时 84 秒，输入 3,257、输出 1,264 token，花费 0.00081 美元。`parse_chapter_analysis` 解析成功，5 个人物、10 个事件，unanchored 为 0。另有 6 章（第一百四十三至一百四十九章之间）并发，全部解析成功，保留 74 条，锚定失败 4 条，约 5%。
- **对计划的影响：**
  - Q3 说「费用不构成约束」，在这个端点上不成立。按全书 357 万字、1.8 字/token、每章平均输出约 1,080 token 估算，现有 prompt 跑一遍 analyze 约 0.75 美元，已经贴着每天 1 美元的上限。v2 输出更多，一天跑不完。钱的上限实际成了吞吐上限。
  - 并发 6 时约每分钟 3.5 章，全书约 6 小时。这是拿 6 个样本粗估的，没测过稳态。
  - 失效指纹只记实际发出去的参数（temperature、top_p、max_tokens），不要照搬 Qwen3 的 top_k、min_p 等。
  - 客户端把并发压在 8 以内，遇到 429 按 `retry-after` 退避。
- 用户随后指定改测 b.ai 上的 `qwen3.8-flash`，并确认它目前免费。`/models` 里它的 `owned_by` 是 `mixai`，同系列的 `qwen3.8-max` 是 `ali`，走的是转售渠道。下面五项在它上面测：
  1. **支持 JSON schema。** 同样让它照抄越界的 enum 值加多余字段：`json_schema` 下 enum 值被换成了枚举内的值，多余字段也没了，开关思考结果一样；`json_object` 下原样照抄。`moments[].kind` 可以在解码阶段约束。
  2. **上下文。** `/models` 不给上下文长度。实测发 146,820 字，计 86,604 个 prompt token，首行和末行都答对，没有截断。中文约 1.7 字/token（章节 prompt 实测 1.69–1.77）。`max_tokens` 最大 131,072，超过返回 400。
  3. **并发和限流。** 响应头里没有任何限流字段。同时发 16 个小请求，全部成功，没有 429，上限没摸到。关思考后 6 章并发，单章 17–63 秒，整批耗时由最慢的一章决定（28–63 秒）；生成 46–61 token/s。
  4. **思考模式默认开启，必须显式关掉。** 思考内容单独放在 `message.reasoning_content`，`content` 里只有 JSON。`enable_thinking: false`、`chat_template_kwargs: {"enable_thinking": false}`、`thinking: {"type": "disabled"}` 三种写法都能关：关掉后 `reasoning_tokens` 为空，同一道题输出从 429 token、9.2 秒降到 6 token、1.9 秒，没有藏起来照算。`reasoning_effort: "low"` 关不掉，照样思考 261 token。开着思考有三个代价：
     - 慢。第二十一章输出 11,283 token，其中思考 10,018，耗时 177 秒；关掉后 1,254 token、21 秒。同样 6 章并发，整批 250 秒对 28 秒。
     - `max_tokens` 只限正文，不限思考。传 40 时，开着思考输出了 274 token，其中思考 229，正文被截断；传 4096 时实际输出 11,283。
     - 采样参数看不出效果，见下一条。
  5. **采样参数。** `top_k`、`min_p`、`presence_penalty`、`frequency_penalty`、`repetition_penalty`、`seed` 一起传，返回 200。关思考后，`temperature=0` 连跑 3 次，前 7–13 个字相同，之后分叉；temperature 1.5 加 `top_k=1`，前 18–30 个字相同，文字通顺；temperature 1.0 对照从第一个字起就不同。参数看起来生效了，但同样的参数不能复现。开着思考时，`temperature=0` 也从第一个字起就不同。
- **冒烟调用通过。** 关思考、用 `json_schema`，同样 7 章（第二十一章，加第一百四十三至一百四十九章之间 6 章）跑了 3 轮，21 次全部解析成功，保留 265 条，锚定失败 23 条，8.0%。开着思考跑 1 轮，保留 99 条，失败 4 条，3.9%。Fisher 精确检验 p=0.18，样本太小，分不出是思考的作用还是波动。只传 temperature、top_p 和传全套 Qwen3 参数各跑一轮，失败率 8.2% 对 8.3%，没有差别。失败的引文逐条看过：大多是模型用「……」把两段不挨着的原文拼成一句，开关思考都有；只有 2 条是改了字。
- **对计划的影响（如果选它）：**
  - 请求里写死关思考。和 Ollama 的 `think: false` 一样，不做成配置，也不进失效指纹：一个不会变的值，记进指纹也比对不出什么。真正的风险是上游是转售渠道，哪天开关不生效，输出会悄悄变。思考内容单独返回，所以看得出来：响应里 `reasoning_tokens` 或 `reasoning_content` 不为空时，generator 直接报错，这一章不写进派生物。
  - 只读 `message.content`。不要把 `reasoning_content` 拼进 `parse_json_object`：它解析失败时会截取第一个 `{` 到最后一个 `}`，思考过程里常有半截 JSON。
  - `kind` 用 `json_schema` 约束。
  - 传不传全套采样参数，对锚定失败率没有可见影响。指纹照样只记实际发出的参数。
  - 关思考、并发 6 时约每分钟 7–13 章，全书约 1.5–3 小时。限流上限和稳态都没测过。
- 两个端点失败的引文都有省略号拼接。v2 的 prompt 要写明：引文必须是一段连续的原文。

## 未决

### Q5 · 章节识别与进度锚点

**已知事实：**
- `CHAPTER_RE` 是 `第[数字]+[章节卷回部篇].*` 或 `(序章|楔子|引子|尾声|后记|番外).*`，不限行长，也不限标点。
- 宽正则匹配 1210 个。此前记录的「窄正则 `第X[章节卷回]` 匹配 1138 个，多出的 72 个是部、篇、序章等」在当前源文件上复现不出来：窄正则同样匹配 1210 个，部、篇、序章这几类一个都没有。见下面的测量结果。
- runbook 里「第四卷的长度比前面三卷的哪一卷都更长」被当成章节，该章长 30,905 字。
- `SKILL.md` 规定 `--max-chapter N` 指第 N 个被识别出的标题，而读者说的是书里自己的「第 N 章」。

**两个假设：**
1. 卷标题、序章等被计入序号，导致序号与书内章号错位。这是少给信息的方向，安全但缺上下文。
2. 「第四卷……」之后 3 万字里没有识别出任何标题。要么那一段本来就没有章标题，要么那里的标题格式正则认不出。后一种情况会少识别标题，是剧透的方向。

**测量项**（都不需要调用模型）：
1. 各类标题（章、节、卷、回、部、篇、序章等）分别匹配到多少个。
2. 列出含 `，。！？` 或超过 30 字的匹配行。
3. 列出相邻标题之间字数异常大的区间。
4. 列出像标题但没被匹配上的行，比如 `^\s*[【\[（(]?\s*第.{1,8}[章节回]`。
5. 解析「第 N 章」里的数字，检查是否逐一递增。跳号说明漏识别了，重号说明卷内重新编号或有误报。

**测量结果**（2026-09-14，源文件 176,084 行、357 万字）：

1. **各类计数**：章 1201，卷 9。节、回、部、篇、序章、楔子、引子、尾声、后记、番外全部为 0。
   - 9 个「卷」没有一个是卷的开头：6 个是「第X卷卷末小结/总结/感言」，1 个是「第五卷，焉知二百载，完」，另外 2 个是卷末感言里以「第四卷」开头的正文段落（33 字和 106 字，后者就是 runbook 里那个 30,905 字的「章」）。
   - 全书没有卷开头的标题，卷边界只能靠章号重置推出来：章号 6 次回到 1，共 7 卷，起点在 L9、L13093、L34938、L57138、L103027、L127973、L155418。卷尾另有 `【第一卷：独在异乡为异客，完】` 这类收尾行，正则不匹配。
2. **含 `，。！？` 或超过 30 字的匹配行**共 56 个，其中 54 个是真章名（如「第八章 沧海桑田，仇寇犹在」），误报只有上面那 2 段感言。按标点排除会误杀 54 个真章名。按长度也分不开：最长的真章名「第三百三十二章 Do you hear the people sing?」有 36 字，比 33 字那段感言还长。
3. **相邻标题间字数**：中位数 2,175，p90 3,363，p95 6,105，最大 27,073。
   - 最大的 27,073 字在「第四卷的长度……」之后：感言的后半段，加上一整篇番外。番外按 `001`–`009`、`外一篇01`–`03` 分成 12 节，一节都没识别出来。

## 设计

### `analyze` v2：原子笔记（Q12）

升级方式：`ANALYSIS_SCHEMA_VERSION` 2 → 3，`ANALYSIS_PROMPT_VERSION` 改为 `chapter-analysis-v2`，现有 `analysis.json` 作废重建。每章调用一次，各章之间可以并行。输出三部分：

- **`summary`**：沿用现有规则，整章都在进度内才显示。
- **`moments[]`**：取代现在的 `characters` / `events`。每条包含：
  - `characters`：原文里的称呼。
  - `kind`：用 JSON schema 的 enum 约束，只能取「抉择 / 冲突 / 战斗 / 揭示 / 情感 / 关系变化 / 成长 / 其他」之一。靠解码阶段约束，而不是像图谱那样事后丢弃。
  - `description`：一句话描述。
  - `trait`：体现的性格侧面，可以为空。
  - `importance`：重要度 1–5，只在本章内部评定，跨章不完全可比，最终挑选由 agent 负责。
  - `evidence`：原文引文。
- **`identities[]`**：本章原文明确说出的身份或别名关系，比如「蒙面人就是约格」，同样带原文引文。

引文处理：
- 沿用 `locate_evidence` 的宽松匹配，以及 `analysis._resolve_evidence` 在本章各 chunk 之间回退查找的逻辑。锚定失败的条目丢弃并计入 `unanchored_count`。
- 引文要解析到**精确的源文件行号**。映射时走 TextUnit 的行号，或者在源文件中该 chunk 的字节区间内重新定位；不能在 `chunk.text` 里数换行。

称呼与输出预算（来自 v1 前 50 章试跑）：
- `characters` 里每个称呼单独一项，照原文写，不加括号注释或斜杠。
- Q15 的越界检查排在任何名字清洗之前。后文才出现的名字要丢掉整条 moment，不能先删掉这个称呼，让 moment 绕过检查。
- `num_predict` 按 v2 小批试跑的实际输出长度来定，不按 v1 顶到上限的次数来定。

### 人物身份归并：分两遍（Q13）

身份合并本身就可能剧透。如果第 300 章揭示了身份，全局合并后，只读到第 100 章的读者会在真名的时间线里看到蒙面人的片段。

- **第一遍**：就是 `analyze` v2，并行运行，产出 `moments` 和 `identities`。
- **第二遍**：按章节顺序串行。每章的输入只有：本章 moments 里的称呼及其一句话描述、本章的 `identities`、截至上一章的人物表。不含正文。输出是把称呼归入已有人物或新建人物。
- **每条身份关系都记录确立章节和原文引文**。引文锚定不上的关系不合并。
- **查询时**：进度为 N 时，只使用确立章节 ≤ N 的关系。
- 人物表是 `analysis.json` 的派生物。`analysis.json` 失效时，人物表必须 fail closed。
- 第二遍不给正文，新的身份关系只能引用第一遍已经锚定的 `identities` 引文，不能凭描述相似另建关系。
- 同名异写（作者笔误或下载源问题）以后手动聚类时，规则不变：两种写法各自锚定原文，确立章节取较晚出现的那种写法。不为人工合并开免引文的例外。

### 防止模型把已知的后文写进笔记（Q15）

云端模型很可能读过这本网文。引文锚定管不住模型自己写的文字里混进的后文信息。

- **检查方法**：人物表建成后，对每个名字及别名，用纯字符串查找算出它在源文件里首次出现的行。
- **适用范围**：所有模型写出的文字，包括 moment 的 `description` / `trait` / `characters`、章梗概、剧情段名称和梗概。只要出现了一个首次出现晚于该单元末行的人名，就判为越界。
- **越界后怎么处理**：沿用 AGENTS.md 里「条目级丢弃、文档级重试」的边界。
  - moment 丢弃，并单独计数落盘，与 `unanchored_count` 同样处理，字段名实现时再定。
  - 梗概、剧情段文字属于文档级失败，触发重试。
- **局限**：只能拦住人名，拦不住「他日后会背叛」这类不含人名的后文信息。这部分靠 prompt 里「只根据本章」的约束，再用评估集的进度截断题抽查。

### 剧情段索引（Q6、Q14）

- **结构**：连续分段，每章只属于一个剧情段。分「卷 → 剧情段」两层；如果 Q5 测出卷标题识别不可靠，就只做剧情段一层。
- **切分**：在每卷内部，用有重叠的滑动窗口扫逐章梗概，由模型标出分段点并起名。重叠区的边界按多数表决确定。窗口大小按 qwen3.8-flash 的上下文长度确定：标称值查不到，实测 8.6 万 token 没有截断。
- **每段内容**：名称、别名、章节范围、梗概。梗概基于该段的逐章梗概生成。
- **可见性**：只有整段都在进度之内的剧情段才会出现。读到一半的段不列出，名称和章节范围都不显示。
- 多线交替叙事的故事线不单独建模，由人物时间线兜底。

### 查询命令（Q16）

全部走同一套进度过滤。按 AGENTS.md 的分层约定，逻辑放在 `app.py`，`cli.py` 只做 adapter。

| 命令 | 返回 |
|---|---|
| `arcs` | 进度内**整段读完**的剧情段，含名称、别名、章节范围、梗概 |
| `arc <名称\|章节范围>` | 该段或该范围内的 moments，按重要度降序。按名称查只能查到整段读完的剧情段 |
| `timeline <人物>` | 该人物的 moments，按章节顺序。支持 `--kind` / `--min-importance` / `--chapters` 筛选 |
| `fetch-range --chapters a-b` | 取原文，自动截到进度以内 |

- **输出预算**：宁可漏掉，agent 会再查；不能用无关内容塞满它的上下文。
  - `arc` / `timeline` 默认 `--min-importance 3`，最多 40 条；截断时打印「另有 X 条未显示」。
  - `fetch-range` 超过 6 万字时截断，并提示缩小范围。
- **进度外的名字**：如果人物只在进度之后出现，或者某个别名是在进度之后才确立的，`timeline` 的输出要和「查无此人」完全一样，不能暴露后文里存在这个名字（与 `SKILL.md` 的规则一致）。

## 评估集（Q4、Q10）

1. **用户出题**：写 10–15 个真实问题，只写问题本身和大致位置，比如「XX 任务」「第几卷」。
2. **云端模型草拟标准场景**：阅读对应章节，为每题给出行号区间、原文引文，外加一句理由。引文用 `locate_evidence` 锚定，对不上原文的丢弃。
3. **用户审核**：逐条勾选或删改。
4. **程序生成截断变体**：每题生成 1–2 个进度停在该段中间的版本。期望标准场景只剩进度内的部分，且越界行数为 0。截断变体用来检验 `timeline`、`arc <章节范围>` 和 `fetch-range`；按 Q16，读到一半的剧情段本来就不应出现在 `arcs` 里。

- **指标**：场景召回率（标准场景的行区间被返回证据覆盖的比例），加上越界行数必须为 0。
- **基线**：在第 4 步动工之前，在现有系统上量一次。「返回证据」怎么算，在建评估集时定下，新旧系统用同一口径。
- **存放位置**：评估集含原文引文，放在 git 忽略的目录里，比如 `metadata/<collection>/`。仓库是公开的，不能提交进去。
- 问题必须由用户出。如果由模型出题，而派生物也是同类模型建的，就等于自己考自己。

## 搁置与剪掉的分支

**搁置**，评估集建好后按需重开：

- **查询端 instruction**：只改 `semantic_search` 的查询侧，不用重建索引。在第 8 步顺带测量。
- **检索粒度解耦**：现在一个 2400 字的 chunk 同时充当 embedding、引用、进度过滤、LLM 抽取四种单元。`analyze` v2 的精确行号已经解决了 E 类问题的引用粒度。只有当评估集显示召回或进度粒度不够时，才考虑「小段检索、大段给上下文」。
- **预先写好的人物小传与前缀摘要树**：把进度 N 拆成最多 log₂N 块预先写好的总结。只有当评估集显示 agent 现场汇总时间线的质量或速度不够时，才重开。
- **引文省略号回退**：引文在省略号处切段，各段在同一个 chunk 里按顺序找到后，取回整段原文。
  - 现在不改 v1：第 2 步重建索引后 v1 的分析整份失效；不升版本就续跑，一个 run 里会混用两种锚定标准；图谱也调用同一个 `locate_evidence`。
  - 第 4 步之后，只有评估集显示关键场景确实因为这类失败丢掉，才重开。
  - 重开时要做到：用含源 chunk 和完整响应的固定输入对比新旧解析；新收下的条目逐条核对原文是否支持描述；处理多处匹配的歧义和引文长度；升版本号；图谱的解析行为不变。

**剪掉**：

- **rerank**：Ollama 不支持，且 Q2 已定由 agent 自己排序。
- **进度过滤召回补偿**：已核实过滤是精确的。
- **查询改写、HyDE、multi-query**：同样由 Q2 排除。
- **全自动出题**。
- **重型 GraphRAG**：沿用 `docs/architecture-archive.md` 的结论。
- **人工合并免引文**：见 Q13。
- **随手抽几章量梗概错误率**：几章样本给不出可信的比例。已发现的错误类型直接进第 4 步的人工核对清单。
