# 叙事索引规格：剧情段高光与人物塑造

日期：2026-09-14
状态：**已定稿，未实施**。章节识别（Q5）留待在 GPU 机器上测量后再定。
来源：一次 grilling 会话。问题是「针对项目需求，算法层面有没有更好的解法」。Q 编号沿用会话里的编号。

在 GPU 机器上开工时，从文末「执行顺序」第 0 步开始。

## 不重新讨论的事

- **核心需求是 E 类问题**：某段剧情或某个任务的**高光**，以及**人物塑造**。事实定位、关系查询、前情提要都是次要的。（Q1）
- **查询由 agent 规划**。ReadFellow 只提供精确、便宜、防剧透的基础命令。查询改写、HyDE、multi-query、工具内 LLM rerank 都不做。（Q2）
- **离线派生允许调用云端模型**，用第三方免费接口上的 GLM 5.3 Flash，费用不构成约束。查询时的 embedding 继续用本地 Ollama `qwen3-embedding:8b`。（Q3、Q9）
- **评估集先行**。任何会改变排序的改动都要在评估集上对比。例外：对错由三条不变量判定的修正，比如章节识别，不走评估集。（Q4）
- **离线只产原子笔记，由 agent 在查询时汇总**。不预先写人物小传或剧情段总结。短剧情段靠 `fetch-range` 让 agent 读原文。（Q7）
- **图谱冻结**：不再投入、不重建，现有产物继续给 `hybrid` 做标注。等新派生物在评估集上胜出，再决定是否退役。（Q8）
- **原地升级 `analyze`**，不另建派生物。（Q12）
- **人物身份分两遍归并**。每条身份关系都带「在哪一章确立」，查询时只使用进度之内确立的关系。（Q13）
- **剧情段连续切分**，分「卷 → 剧情段」两层。只有整段读完的剧情段才会出现在输出里。（Q6、Q14、Q16）
- **防止模型把已知的后文写进笔记**，用确定性的人名检查兜底。（Q15）

## 为什么现有机制对不上 E 类问题

- **`hybrid` 返回最相似的前几个 chunk**（`search.top_k` 默认 5）。高光要的是覆盖一段剧情后按重要性挑选；人物塑造要的是全书分散的场景按时间排列。两者都不是相似度前几名。`hybrid` 仍然适合用来定位模糊描述的某一段。
- **图谱用封闭关系词表记录事实边**。被它当作叙事长尾丢掉的谓词（`怀疑`、`担心`、`回答`，全量占 20.7%）恰恰是人物塑造的素材。
- **`analyze` 是最接近的现有机制**：它逐章给出梗概、人物作用和事件，并且锚定了原文。但每章上限 8 个人物、10 个事件，没有重要度，也没有跨章结构。

## 已核实的事实

**zvec 按进度过滤是精确的。**
- `VectorSchema` 不传 `index_param` 时默认是 Flat 索引（`zvec/model/schema/field_schema.py:238-239`）。`store.py` 没有传。
- filter 在向量检索之前计算，检索过程中边查边过滤（`src/db/sqlengine/planner/vector_recall_node.cc:138,168-169`）。
- 在 0.6.0、2307 条 × 4096 维上实测：放行比例降到 0.9% 时 recall@20 仍为 1.000，越界 0 条。返回条数为 `min(topk, 可见文档数)`。
- 如果以后改用 HNSW，要重新验证。

**Qwen3-Embedding 的查询端 instruction。**
- 官方格式是 `Instruct: {task}\nQuery:{query}`。只加在查询端，文档端不加；中文任务的 instruction 也用英文写。
- 来源：https://github.com/QwenLM/Qwen3-Embedding README 第 93-94、103 行；`evaluation/task_prompts.json`。
- Ollama 的 `/api/embed` 不套用任何模板（v0.34.0 `server/routes.go:800-976`），前缀必须由调用方自己拼。
- 官方只笼统说能提升 1–5%，这本书上没有测过。

**Ollama 没有 rerank 端点（截至 v0.34.0）。**
- 相关需求 issue #3368 至今仍 open。
- `/api/generate` 从 v0.12.11 起支持 `logprobs`，理论上可以做 yes/no 打分，但没有验证。

**代码里的坑。**
- `read_text_units` 会丢掉空行，所以 `chunk.text` 里不含空行，在里面数换行得不到源文件行号。
- `chapter_char_budget` 按 Ollama 的 `num_ctx` 计算上下文预算。

## 未决

### Q5 · 章节识别与进度锚点

**已知事实：**
- `CHAPTER_RE` 是 `第[数字]+[章节卷回部篇].*` 或 `(序章|楔子|引子|尾声|后记|番外).*`，不限行长，也不限标点。
- 宽正则匹配 1210 个，窄正则 `第X[章节卷回]` 匹配 1138 个。多出的 72 个按构造都是部、篇、序章、楔子、尾声、后记、番外这几类行。
- runbook 里「第四卷的长度比前面三卷的哪一卷都更长」被当成章节，该章长 30,905 字。
- `SKILL.md` 规定 `--max-chapter N` 指第 N 个被识别出的标题，而读者说的是书里自己的「第 N 章」。

**两个假设：**
1. 卷标题、序章等被计入序号，导致序号与书内章号错位。这是少给信息的方向，安全但缺上下文。
2. 「第四卷……」之后 3 万字里没有识别出任何标题。要么那一段本来就没有章标题，要么那里的标题格式正则认不出。后一种情况会少识别标题，是剧透的方向。

**测量项**（都不需要调用模型）：
1. 各类标题（章、节、卷、回、部、篇、序章等）分别匹配到多少个。
2. 列出含 `，。！？` 或超过 30 字的匹配行。
3. 列出相邻标题之间字数异常大的区间。
4. 列出像标题但没被匹配上的行，比如 `^\s*[【\[（(]?\s*第.{1,8}[章节回]`。
5. 解析「第 N 章」里的数字，检查是否逐一递增。跳号说明漏识别了，重号说明卷内重新编号或有误报。

**量完再在三个选项里定：**
- **A**：在 `progress.py` 里解析标题中的数字，让 `--max-chapter 50` 指书里的「第五十章」。同一个号出现多次时报错并列出候选。不改 chunk，不用重建。
- **B**：收紧识别规则（限行长、排除句读）。这会改变 chunk 边界，要升 `CHUNKER_VERSION`，然后重建索引（约 12 分钟）和 `analyze`。
  - 如果选 B，还要同时决定：冻结的图谱会随之失效，`hybrid` 标注就会消失。要么用 GLM 重建一次图谱，要么接受标注消失。
- **C**：维持现状。

会话里的建议是先做 A，B 与其他切块改动一起重建，但用户保留了意见。「卷」这一层能否用于剧情段索引，也取决于这次测量。

## 设计

### `analyze` v2：原子笔记（Q12）

升级方式：`ANALYSIS_SCHEMA_VERSION` 2 → 3，`ANALYSIS_PROMPT_VERSION` 改为 `chapter-analysis-v2`，现有 `analysis.json` 作废重建。每章调用一次，各章之间可以并行。输出三部分：

- **`summary`**：沿用现有规则，整章都在进度内才显示。
- **`moments[]`**：取代现在的 `characters` / `events`。每条包含：
  - `characters`：原文里的称呼。
  - `kind`：用 JSON schema 的 enum 约束，只能取「抉择 / 冲突 / 战斗 / 揭示 / 情感 / 关系变化 / 成长 / 其他」之一。靠解码阶段约束，而不是像图谱那样事后丢弃。
  - `description`：一句话描述。
  - `trait`：体现的性格侧面，可以为空。
  - `importance`：重要度 1–5，只在本章内部评定，跨章不完全可比，最终挑选由 agent 负责。
  - `evidence`：原文引文。
- **`identities[]`**：本章原文明确说出的身份或别名关系，比如「蒙面人就是约格」，同样带原文引文。

引文处理：
- 沿用 `locate_evidence` 的宽松匹配，以及 `analysis._resolve_evidence` 在本章各 chunk 之间回退查找的逻辑。锚定失败的条目丢弃并计入 `unanchored_count`。
- 引文要解析到**精确的源文件行号**。映射时走 TextUnit 的行号，或者在源文件中该 chunk 的字节区间内重新定位；不能在 `chunk.text` 里数换行。

### 人物身份归并：分两遍（Q13）

身份合并本身就可能剧透。如果第 300 章揭示了身份，全局合并后，只读到第 100 章的读者会在真名的时间线里看到蒙面人的片段。

- **第一遍**：就是 `analyze` v2，并行运行，产出 `moments` 和 `identities`。
- **第二遍**：按章节顺序串行。每章的输入只有：本章 moments 里的称呼及其一句话描述、本章的 `identities`、截至上一章的人物表。不含正文。输出是把称呼归入已有人物或新建人物。
- **每条身份关系都记录确立章节和原文引文**。引文锚定不上的关系不合并。
- **查询时**：进度为 N 时，只使用确立章节 ≤ N 的关系。
- 人物表是 `analysis.json` 的派生物。`analysis.json` 失效时，人物表必须 fail closed。

### 防止模型把已知的后文写进笔记（Q15）

GLM 很可能读过这本网文。引文锚定管不住模型自己写的文字里混进的后文信息。

- **检查方法**：人物表建成后，对每个名字及别名，用纯字符串查找算出它在源文件里首次出现的行。
- **适用范围**：所有模型写出的文字，包括 moment 的 `description` / `trait` / `characters`、章梗概、剧情段名称和梗概。只要出现了一个首次出现晚于该单元末行的人名，就判为越界。
- **越界后怎么处理**：沿用 AGENTS.md 里「条目级丢弃、文档级重试」的边界。
  - moment 丢弃，并单独计数落盘，与 `unanchored_count` 同样处理，字段名实现时再定。
  - 梗概、剧情段文字属于文档级失败，触发重试。
- **局限**：只能拦住人名，拦不住「他日后会背叛」这类不含人名的后文信息。这部分靠 prompt 里「只根据本章」的约束，再用评估集的进度截断题抽查。

### 剧情段索引（Q6、Q14）

- **结构**：连续分段，每章只属于一个剧情段。分「卷 → 剧情段」两层；如果 Q5 测出卷标题识别不可靠，就只做剧情段一层。
- **切分**：在每卷内部，用有重叠的滑动窗口扫逐章梗概，由模型标出分段点并起名。重叠区的边界按多数表决确定。窗口大小按 GLM 的上下文长度确定。
- **每段内容**：名称、别名、章节范围、梗概。梗概基于该段的逐章梗概生成。
- **可见性**：只有整段都在进度之内的剧情段才会出现。读到一半的段不列出，名称和章节范围都不显示。
- 多线交替叙事的故事线不单独建模，由人物时间线兜底。

### 查询命令（Q16）

全部走同一套进度过滤。按 AGENTS.md 的分层约定，逻辑放在 `app.py`，`cli.py` 只做 adapter。

| 命令 | 返回 |
|---|---|
| `arcs` | 进度内**整段读完**的剧情段，含名称、别名、章节范围、梗概 |
| `arc <名称\|章节范围>` | 该段或该范围内的 moments，按重要度降序。按名称查只能查到整段读完的剧情段 |
| `timeline <人物>` | 该人物的 moments，按章节顺序。支持 `--kind` / `--min-importance` / `--chapters` 筛选 |
| `fetch-range --chapters a-b` | 取原文，自动截到进度以内 |

- **输出预算**：宁可漏掉，agent 会再查；不能用无关内容塞满它的上下文。
  - `arc` / `timeline` 默认 `--min-importance 3`，最多 40 条；截断时打印「另有 X 条未显示」。
  - `fetch-range` 超过 6 万字时截断，并提示缩小范围。
- **进度外的名字**：如果人物只在进度之后出现，或者某个别名是在进度之后才确立的，`timeline` 的输出要和「查无此人」完全一样，不能暴露后文里存在这个名字（与 `SKILL.md` 的规则一致）。

## 评估集（Q4、Q10）

1. **用户出题**：写 10–15 个真实问题，只写问题本身和大致位置，比如「XX 任务」「第几卷」。
2. **GLM 草拟标准场景**：阅读对应章节，为每题给出行号区间、原文引文，外加一句理由。引文用 `locate_evidence` 锚定，对不上原文的丢弃。
3. **用户审核**：逐条勾选或删改。
4. **程序生成截断变体**：每题生成 1–2 个进度停在该段中间的版本。期望标准场景只剩进度内的部分，且越界行数为 0。截断变体用来检验 `timeline`、`arc <章节范围>` 和 `fetch-range`；按 Q16，读到一半的剧情段本来就不应出现在 `arcs` 里。

- **指标**：场景召回率（标准场景的行区间被返回证据覆盖的比例），加上越界行数必须为 0。
- **基线**：在第 4 步动工之前，在现有系统上量一次。「返回证据」怎么算，在建评估集时定下，新旧系统用同一口径。
- **存放位置**：评估集含原文引文，放在 git 忽略的目录里，比如 `metadata/<collection>/`。仓库是公开的，不能提交进去。
- 问题必须由用户出。如果由模型出题，而派生物也是同类模型建的，就等于自己考自己。

## 搁置与剪掉的分支

**搁置**，评估集建好后按需重开：

- **查询端 instruction**：只改 `semantic_search` 的查询侧，不用重建索引。在第 8 步顺带测量。
- **检索粒度解耦**：现在一个 2400 字的 chunk 同时充当 embedding、引用、进度过滤、LLM 抽取四种单元。`analyze` v2 的精确行号已经解决了 E 类问题的引用粒度。只有当评估集显示召回或进度粒度不够时，才考虑「小段检索、大段给上下文」。
- **预先写好的人物小传与前缀摘要树**：把进度 N 拆成最多 log₂N 块预先写好的总结。只有当评估集显示 agent 现场汇总时间线的质量或速度不够时，才重开。

**剪掉**：

- **rerank**：Ollama 不支持，且 Q2 已定由 agent 自己排序。
- **进度过滤召回补偿**：已核实过滤是精确的。
- **查询改写、HyDE、multi-query**：同样由 Q2 排除。
- **全自动出题**。
- **重型 GraphRAG**：沿用 `docs/architecture-archive.md` 的结论。

## 执行顺序

每步做完、满足完成标准之后，再进入下一步。

0. **接入 GLM 并核实端点能力。**
   - 新增一个云端 `JsonGenerator` 实现。API key 从环境变量读，不写进 `config.yaml`。
   - 派生物的失效指纹要记录**接口地址和模型名**，因为第三方接口可能在同一个模型名下换模型。
   - 核实五件事：
     1. 是否支持 JSON schema 约束输出。不支持就退回 JSON 模式，靠解析校验和重试兜底。
     2. 上下文长度。据此重算 `chapter_char_budget`。
     3. 并发和限流上限。
     4. 是否默认开启思考模式、怎么关闭。qwen3 上吃过这个亏，见 `docs/spec/derivation-hardening-plan.md` 根因 A。
     5. 支持哪些采样参数。`DerivationSettings` 里的 Qwen3 参数不一定全部可用。
   - **完成标准**：用现有 `ANALYSIS_RESPONSE_SCHEMA` 对 1 章做冒烟调用，得到能解析的 JSON；上面几项结果补写进本文档「已核实的事实」。
1. **测量 Q5。**
   - 做完「未决」一节里的 5 项测量。
   - **完成标准**：数字补写进本文档，用户在 A/B/C 中定下选项。
2. **（仅当 Q5 选 B）改切块规则并重建。**
   - 升 `CHUNKER_VERSION`，运行 `index --rebuild`，并决定图谱是否重建。
   - **完成标准**：`status` 显示索引 N/N。
3. **建评估集并量基线。**
   - **完成标准**：至少 10 道经用户审核的题及其截断变体；基线的场景召回率和越界行数已记录。
4. **`analyze` v2，并行运行。**
   - **完成标准**：所有完整章节都已处理，超预算被跳过的章节逐一列出；`unanchored` 占比已记录。
5. **人物身份归并。**
   - **完成标准**：每条身份关系都带确立章节和引文；抽一个身份揭示点验证：进度设在揭示之前时，时间线里没有被合并进来的片段。
6. **切剧情段。**
   - **完成标准**：每章恰好属于一个剧情段，无缺口、无重叠；名称和梗概全部通过 Q15 检查。
7. **实现查询命令并更新 `SKILL.md`**，补上 E 类问题的流程：`arcs` → `arc` → `fetch-range` → 引用；人物塑造走 `timeline`。
   - 测试只覆盖需求规定的语义：读到一半的剧情段不出现；进度 N 只使用确立章节 ≤ N 的身份关系；`fetch-range` 截到进度以内；进度外的名字与查无此人不可区分。
   - **完成标准**：`uv run pytest` 通过，ruff clean。
8. **在评估集上对比新旧系统，并顺带测量查询端 instruction。**
   - **完成标准**：新旧场景召回率对比已记录，所有题的越界行数为 0。然后用户决定图谱是否退役。
